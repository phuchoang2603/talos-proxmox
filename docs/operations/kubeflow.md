# Kubeflow (prod)

The prod platform owns cert-manager, Istio ambient, the NVIDIA GPU operator, ESO/Doppler, local-path storage, and one shared Argo Workflows controller. The Kubeflow applications below are prod-only; no second copies of these shared controllers are installed.

## Ownership and versions

- `apps/components/auth` supplies Dex 2.45.1 and OAuth2 Proxy 7.15.5. The chart uses external Secrets from the `doppler` ClusterSecretStore; no password, cookie secret or OIDC client secret is checked in. Both services run in `auth`.
- `apps/components/knative` supplies Serving and Eventing 1.23.0 with the cluster-local Istio gateway in `istio-system`. The ingress Gateway workload belongs to the shared `apps/components/istio` chart, enabled for prod only as an internal ClusterIP.
- `apps/components/kubeflow` enables the shared components from Community Distribution master revision `1e37b5db692624f65de04f30d5989e9651f20492` (2026-10-05): Trainer 2.3.0, Notebooks v1 1.11.0, Dashboard 2.0.0 with Profiles/KFAM, Katib 0.19.0, KServe and its UI 0.21.0/1.0.5, and Hub Catalog 0.3.17. The fraud repo owns its Profile and Hub Registry instance. Spark Operator 2.5.2 is the platform chart's only Helm dependency. The pinned upstream Kustomize outputs live in `files/`; the upstream sample passwords are removed. Kubernetes-native KFP is explicitly non-production upstream. Treat this prod-only deployment as experimental and do not use it with production data until end-to-end tests pass.
- Pipelines runs unreleased KFP master (3.0 development) from `kubeflow/pipelines` commit `ceb76061bf268f3ca10d6611b4daf8e8c78e64b7` (2026-10-06), with all images pinned to the immutable CI tag `run-37518086931-1`. Master removes ML Metadata, which is what limited KFP 2.x on PostgreSQL. It uses the single-user Kubernetes-native API on the CNPG `mlpipeline` database over TLS (`sslmode=verify-full` against the `kubeflow-pipelines-db-ca` CA). The API server runs `CREATE DATABASE` on every start, so the `kfp` role has CREATEDB. `files/pipeline/000.yaml` is rendered by `kubectl kustomize apps/components/kubeflow/vendor/pipeline`; re-render after changing that overlay or its pinned commit, and keep the image tags, `V2_DRIVER_IMAGE` and `V2_LAUNCHER_IMAGE` on the same build. The UI only reads artifacts from origins in `ALLOWED_ARTIFACT_ENDPOINTS`. Upgrading from 2.17.2 needs a one-time `kubectl patch` that replaced the UI Deployment strategy with `{type: Recreate}`: server-side apply cannot remove the defaulted `rollingUpdate` field. Since 2.18, pipeline uploads must name a namespace and viewing logs needs the `readLog` permission. Workspaces v2 is pre-GA and deliberately excluded.
- `apps/components/argo-workflows` remains the only Argo controller. Its workflow namespaces include `kubeflow`, the consumer-owned `fraud-ml-prod` Profile and the separate `fraud-data-prod` historical source workload. The KFP overlay excludes the upstream Argo controller, its RBAC and configuration, and bundled MySQL and SeaweedFS; master has no v1 cache server. The `kubeflow` Namespace and its ambient and Pod Security labels belong only to the `kubeflow` Application; a second Application applying the same Namespace with the shared Argo CD field manager strips those labels. Local edits to the other vendored outputs: sidecar injection is disabled (ambient only), the Profile controller's hard-coded `istio-injection=enabled` label is removed from Profile namespaces, the Jupyter, TensorBoards and Volumes web apps and the Dashboard carry resource requests and a memory limit (upstream sets none), the Profile controller's probes use a 5s timeout instead of the 1s default, and upstream NetworkPolicies in `kubeflow` and `knative-serving` allow the ambient kubelet probe source `169.254.7.127/32` and HBONE port 15008. KFP retains its application controllers but uses two CNPG PostgreSQL clusters (KFP and Katib), an external RustFS bucket, and an artifact repository in `kubeflow`; the consumer owns its namespace-specific repository. It does not run bundled MySQL, PostgreSQL, SeaweedFS, or a second Argo controller.

The platform chart owns the Kubeflow Istio ingress configuration, not any user Profile. The Profile controller creates namespaces with the ambient mesh label. The prod-only `fraud-ml-prod` Profile, Hub Registry, registry database ExternalSecret, RustFS ExternalSecret, KFP launcher, and Argo artifact configuration are managed by `../realtime-credit-card-fraud-detection/infra/charts/kubeflow-workspace`. The consumer's Profile owner must match the Dex login identity configured in `apps/components/auth/values.yaml`. The consumer root must reconcile after the platform's CRDs and controllers; its child Application retries missing-CRD/namespace failures. Do not pre-create the Profile namespace with Argo CD `CreateNamespace`.

## Prerequisites before reconciliation

1. Authentication keys `AUTH_DEX_PASSWORD_BCRYPT`, `AUTH_OIDC_CLIENT_SECRET`, and `AUTH_OAUTH2_COOKIE_SECRET` are seeded in Doppler project `talos-proxmox`, config `prod`. A randomly generated login password is stored **only** in Doppler as `AUTH_DEX_PASSWORD`; retrieve it locally with `doppler secrets get AUTH_DEX_PASSWORD --plain --project talos-proxmox --config prod` (the command prints the secret). Do not commit or paste the password. ExternalSecrets must become Ready before testing login.
2. `KUBEFLOW_RUSTFS_ACCESS_KEY`, `KUBEFLOW_RUSTFS_SECRET_KEY`, `KUBEFLOW_KFP_POSTGRES_PASSWORD`, `KUBEFLOW_KATIB_POSTGRES_PASSWORD`, and `KUBEFLOW_CATALOG_POSTGRES_PASSWORD` remain in the platform Doppler project's `prod` config. The consumer owns its Hub Registry password, RustFS credential copies, and read-only ESO service token in the `realtime-credit-card-fraud-detection` Doppler project's `prd` config. The platform copy of `KUBEFLOW_REGISTRY_DB_PASSWORD` was removed after a verified transfer; neither repo stores secret values. The versioned RustFS bucket `kubeflow-prod-pipelines` and bucket-scoped service account were created and tested with an object round trip on October 6, 2026. The four obsolete KFP/Katib MySQL and SeaweedFS keys were removed from platform prod Doppler on October 6, 2026. Test a real KFP artifact upload after reconciliation. The upstream Hub Catalog still uses an ephemeral PostgreSQL volume and needs durable storage and backups before real data is stored.
3. Kubeflow is published at <https://kubeflow.phuchoang.sbs> through the prod Cloudflare tunnel. The `kubeflow` chart's `TunnelBinding` in `istio-system` targets the ClusterIP ingress gateway on port 80. Cloudflare terminates TLS and redirects `http://` to HTTPS (the zone's "Always Use HTTPS" setting). Anonymous requests are redirected to Dex at `https://auth.phuchoang.sbs/dex`. Log in as `identity.email` with `AUTH_DEX_PASSWORD`. Dex's issuer is the public URL. OAuth2 Proxy and Istio fetch tokens and signing keys from Dex's in-cluster address, and the session cookie is HTTPS-only and limited to `kubeflow.phuchoang.sbs`. The port-forward login on `localhost:8080` no longer works. **This experimental deployment is reachable from the internet**: only the single Dex identity passes the OAuth2 Proxy and JWT policies, and Dex has no lockout, so keep `AUTH_DEX_PASSWORD` random and consider a Cloudflare rate-limit rule on `auth.phuchoang.sbs`. The auth chart refuses to render a non-HTTPS issuer or redirect.
4. Reconcile the platform before the consumer root. The Profile controller creates `fraud-ml-prod` with `istio.io/dataplane-mode: ambient`; the consumer's workspace and separate generic secret-store Applications retry until that namespace and the platform CRDs exist. Once the namespace exists, provision `fraud-doppler-token` in it with key `dopplerToken` from the fraud Doppler project's `prd` config; platform ESO cannot read the fraud project. The same generic store runs on dev in `payment-gateway` with its own Doppler `dev` token, without Kubeflow. Both `kubeflow` and `fraud-ml-prod` need their RustFS ExternalSecret, `artifact-repositories` and `kfp-launcher` ConfigMaps ready before starting workflows. A healthy Application alone is not proof of working workloads.

## Validation

Use `devenv shell` for `helm lint` and `helm template` in both repos; supply `--api-versions cert-manager.io/v1/Issuer --api-versions cert-manager.io/v1/Certificate` to template Spark Operator. Check the prod platform and consumer Applications and absence of auth/Knative/Kubeflow on dev. Then verify the ExternalSecrets in both namespaces, both CNPG Clusters, Dex and proxy readiness, Knative Serving and Eventing, KServe webhooks, and the Dashboard at <https://kubeflow.phuchoang.sbs>. Prove one persistent GPU notebook in the consumer Profile, one Kubernetes-native KFP Pipeline/PipelineVersion and a KFP run on the shared Argo controller with a stored RustFS artifact (including upload and download via the UI), one Katib experiment, and authenticated `/pipeline/`, `/jupyter/`, and `/katib/` before declaring the rollout complete. Measure scheduling against the ClickHouse telemetry store, Kafka and other production services; local-path PVCs are node-bound; both CNPG Clusters have one instance and are not HA. Test restore before storing valuable data.

A bounded CUDA smoke Job already passed on prod-server1 on October 6, 2026 (Job `default/kubeflow-gpu-smoke-20261006`, CUDA result 42). This verifies GPU scheduling and execution only; it does not prove Kubeflow workload integration.

The GPU is exposed only through DRA (DeviceClass `gpu.nvidia.com` maps the extended resource `nvidia.com/gpu`), so no node reports `nvidia.com/gpu` capacity and the Jupyter spawner's GPU field lists no vendors. Create GPU notebooks from a Notebook manifest that sets `nvidia.com/gpu` limits. Do not patch node capacity to make the field appear: the scheduler would then account the fake node resource instead of allocating a DRA device.

## Historical DP1 platform prerequisites

Spark Operator's watched namespaces include `fraud-data-prod` alongside `kubeflow`; the fraud application owns the data namespace and SparkApplications. The platform's `datahub` component is enabled for prod and publishes its frontend at `https://datahub.phuchoang.sbs` through the Cloudflare tunnel using Dex OIDC. It installs no additional shared operators. Its pinned official DataHub chart is 1.1.7, server v1.7.0.1; dependencies are CNPG PostgreSQL 16.13, Strimzi Kafka 4.2.1 and OpenSearch chart 2.36.0/image 2.19.5. The installed Strimzi operator advertises Kafka 4.2.1 support. DataHub's supported search integration is OpenSearch 2.x.

The rendered budgets below are requests/limits, before operator overhead; only one DP1 SparkApplication runs at a time. JVM heap leaves room for native allocations. Setup has separate blocking/nonblocking update Jobs, each budgeted below.

| Workload | CPU request / limit | Memory request / limit | JVM heap | Persistent storage |
| --- | --- | --- | --- | --- |
| GMS | 0.5 / 2 cores | 2 / 3 GiB | 1 GiB | PostgreSQL/search/Kafka below |
| Frontend | 0.1 / 1 cores | 768 / 1536 MiB | 512 MiB | None |
| PostgreSQL | 0.25 / 1 cores | 512 MiB / 1 GiB | N/A | 10 GiB local-path |
| Kafka combined broker/controller | 0.5 / 2 cores | 1536 MiB / 2 GiB | 1 GiB | 10 GiB local-path |
| OpenSearch | 0.5 / 2 cores | 2 / 3 GiB | 1 GiB | 20 GiB local-path |

On 2026-10-22, read-only inspection found no DataHub deployment. Node allocatable CPU was 7.5/7.5/3.5 cores and memory about 29.7/14.0/14.0 GiB. Existing requested CPU was 4.825/3.19/2.895 cores and memory 11.89/6.31/6.44 GiB. Instantaneous usage was 4.372/2.242/1.665 cores and 11059/8718/9739 MiB. Steady DataHub requests add 1.85 cores and 6.75 GiB, plus 40 GiB of node-bound PVCs; DP1 adds at least 2 cores and 5 GiB, with setup Jobs temporarily adding 0.5 cores/1 GiB each. This is a preliminary inventory, not rollout acceptance: limits overcommit physical resources, free local-path disk, OpenSearch host requirements, restart placement and measured concurrent peak Spark memory/shuffle still need validation. The component stays gated on the ExternalSecrets and dependency readiness checks below.

Provision the following external keys in platform Doppler `talos-proxmox/prod`: `DATAHUB_SYSTEM_CLIENT_SECRET`, `DATAHUB_TOKEN_SIGNING_KEY`, `DATAHUB_TOKEN_SALT`, `DATAHUB_ENCRYPTION_KEY`, `DATAHUB_POSTGRES_PASSWORD`, `DATAHUB_FRONTEND_USERS` (Java `user.props` content) and `DATAHUB_OIDC_CLIENT_SECRET` (shared with the Dex `datahub` static client). Retain auth/encryption/database keys across restarts. ESO targets contain no inline credentials. The frontend is reachable only through its Cloudflare tunnel hostname; Dex owns login at `/callback/oidc`, and the JAAS user in `DATAHUB_FRONTEND_USERS` remains available as the break-glass admin path at `/login`. GMS authentication is enabled and the private network policy permits application-namespace access on 8080. A separate DP1 token and metadata identity must be restricted and verified by authenticated publication/readback before enabling the consumer.

Render with `helm template datahub apps/components/datahub -n datahub` and render the platform root with `--set cluster=prod --set components.datahub.enabled=true`. The blocking system-update Job is an Argo Sync hook after dependencies, followed by GMS/frontend in wave 2; the upstream PreSync hook would deadlock a fresh deployment of these bundled dependencies. During reconciliation, verify ExternalSecrets, CNPG readiness, Kafka metadata/topics, OpenSearch health, successful blocking/nonblocking update Jobs, authenticated GMS and frontend login. Then restart each stateful dependency and verify metadata/assertions survive; observe the complete DataHub plus Spark run against the budgets above. All dependency clusters have one instance, local-path volumes are node-bound, and this course deployment has no HA or verified backup/restore. Do not remove PVCs or change shared operators during rollback; disable the optional component and stop the consumer workflows while preserving catalog state.
