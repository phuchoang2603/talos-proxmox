# Kubeflow

Both environments own cert-manager, Istio, ESO/Doppler and one shared Argo Workflows controller. Dev uses local-path and its local GPU; prod uses cloud-block storage (GCE PD or AWS EBS); GCP production configures one fixed on-demand L4 worker; production local-model caching remains disabled. Kubeflow uses those shared controllers in each environment.

## Ownership and versions

- `apps/components/auth` supplies Dex 2.45.1 and OAuth2 Proxy 7.15.5. The chart uses external Secrets from the `doppler` ClusterSecretStore; no password, cookie secret or OIDC client secret is checked in. Both services run in `auth`.
- Knative is not installed. KServe's default deployment mode is `Standard`, so an InferenceService is a Deployment and a Service, with ingress creation off; inference is reached through its in-cluster Service. Scale-to-zero is not available; use KServe's HPA, or KEDA for event-driven scaling.
- `apps/components/kubeflow` enables the shared components from Community Distribution master revision `1e37b5db692624f65de04f30d5989e9651f20492` (2026-10-05): Trainer 2.3.0, Notebooks v1 1.11.0, Dashboard 2.0.0 with Profiles/KFAM, Katib 0.19.0, KServe and its UI 0.21.0/1.0.5, and Hub Catalog/Registry 0.3.17. The platform owns the `ml` Profile and KFAM owner binding, Model Registry server/UI and its CNPG database. The pinned upstream Kustomize outputs live in `files/`; the upstream sample passwords are removed. Kubernetes-native KFP is explicitly non-production upstream. Treat this deployment as experimental and do not use it with production data until end-to-end tests pass.
- Pipelines runs unreleased KFP master (3.0 development) from `kubeflow/pipelines` commit `ceb76061bf268f3ca10d6611b4daf8e8c78e64b7` (2026-10-06), with all images pinned to the immutable CI tag `run-37518086931-1`. Master removes ML Metadata, which is what limited KFP 2.x on PostgreSQL. It uses the single-user Kubernetes-native API on the CNPG `mlpipeline` database over TLS (`sslmode=verify-full` against the `kubeflow-pipelines-db-ca` CA). The API server runs `CREATE DATABASE` on every start, so the `kfp` role has CREATEDB. `files/pipeline/000.yaml` is rendered by `kubectl kustomize apps/components/kubeflow/vendor/pipeline`; re-render after changing that overlay or its pinned commit, and keep the image tags, `V2_DRIVER_IMAGE` and `V2_LAUNCHER_IMAGE` on the same build. The UI only reads artifacts from origins in `ALLOWED_ARTIFACT_ENDPOINTS`. Upgrading from 2.17.2 needs a one-time `kubectl patch` that replaced the UI Deployment strategy with `{type: Recreate}`: server-side apply cannot remove the defaulted `rollingUpdate` field. Since 2.18, pipeline uploads must name a namespace and viewing logs needs the `readLog` permission. Workspaces v2 is pre-GA and deliberately excluded.
- `apps/components/argo-workflows` remains the only Argo controller, deployed in `operators` and watching `data` and `ml`. Kubeflow, KServe, JobSet and Trainer resources share `ml`; Kubeflow owns its Namespace and ambient/Pod Security labels. The KFP overlay excludes the upstream Argo controller, bundled databases and SeaweedFS. KFP and Katib each use single-instance CNPG PostgreSQL, external object storage and the artifact repository in `ml`.

The platform chart owns the Kubeflow Istio ingress configuration and the `ml` Namespace. External application charts must target `ml` for ML workloads and `data` for data jobs, update their service references, and avoid owning or deleting the platform Namespace through an application Profile. The platform `namespace-owner` RoleBinding binds the configured Dex owner to `kubeflow-admin` in `ml`, with the KFAM `user` and `role` annotations. The Git-managed `ml` Profile supplies KFAM namespace discovery. The automatic Profile provisioner is disabled; KFAM remains running, and Git owns namespace lifecycle and RBAC. The Profile has no ownership reference on the namespace, and no Profile-generated Istio policy is installed. Self-service namespace registration remains disabled, and contributor bindings must be managed through Git to keep ambient authorization workload-scoped. Their identity must match Dex configuration in `apps/components/auth/values.yaml`.

A bounded CUDA smoke Job already passed on prod-server1 on October 6, 2026 (Job `default/kubeflow-gpu-smoke-20261006`, CUDA result 42). This verifies GPU scheduling and execution only; it does not prove Kubeflow workload integration.

GPU allocation uses the NVIDIA DRA driver on both local dev nodes; the traditional NVIDIA device plugin is disabled. GCP production configures one fixed on-demand L4 worker with the same DRA allocation contract. GPU training stays pending until quota and zone capacity permit the VM to start and the driver publishes its device.

GPU workloads must use explicit namespaced `ResourceClaim` or `ResourceClaimTemplate` references, with `deviceClassName: gpu.nvidia.com`, `spec.resourceClaims` on the pod and `resources.claims` on each GPU container. The pinned Notebooks 1.11.0 CRD currently rejects both DRA fields under `spec.template.spec`, so GPU Notebook support is blocked; the UI dropdown is not a substitute. Jobs, training workloads and KServe Standard predictors must carry the equivalent pod/container fields. The Jupyter GPU-count dropdown and `limits: nvidia.com/gpu` use extended-resource requests, which is not a substitute for DRA claims. The DeviceClass retains its Kubernetes compatibility mapping, but use explicit claims for local dev workloads; production selects its fixed GCP GPU worker. Do not patch Node GPU capacity.

The NVIDIA DCGM exporter collects GPU metrics every 60 seconds with DRA pod attribution enabled. The observability chart installs the Prometheus-compatible ServiceMonitor, PodMonitor, Probe, PrometheusRule and ScrapeConfig CRDs; the VictoriaMetrics operator converts these resources into native scrape and rule resources. NVIDIA's ServiceMonitor is converted into a VMServiceScrape for vmagent; the exporter has read-only ResourceSlice RBAC for DRA device mapping. ## GPU training and benchmark placement

`ClusterTrainingRuntime/gpu-training` provides the PyTorch runtime using the shared `gpu-training` DRA claim template and environment-specific GPU placement. Production defaults to one worker on its fixed L4 node.

`ClusterTrainingRuntime/xgboost-gpu-distributed` uses Trainer 2.3.0's `mlPolicy.xgboost`, one node by default, and one `ResourceClaimTemplate/gpu-training` allocation per worker. Its default image is `ghcr.io/kubeflow/trainer/xgboost-runtime:v2.3.0`, whose bundled NCCL 2.20.5 is incompatible with its XGBoost 3.0.2 GPU collective. Consumers must supply a validated image with compatible CUDA/NCCL (at least NCCL 2.23.4) and clean worker shutdown; consumers override `TrainJob.spec.trainer.image`, command and args with their non-root training image. The runtime supplies restricted-compatible security settings and CPU/memory reservations; it does not request the legacy extended GPU resource. The controller injects `DMLC_*`; rank zero must start `RabitTracker`. GPU collectives use TCP over Cilium (`NCCL_SOCKET_IFNAME=eth0`, `NCCL_IB_DISABLE=1`), with no RDMA/NVLink assumption.

The single production L4 allocation is shared by training and model-server benchmarking. Release model-server claims before training; two-rank training and two-GPU benchmarks require additional provisioned GPU capacity. Keep baseline, batching/parallel-slot and speculative-decoding runs separate; record throughput, TTFT/TPOT, failures and GPU memory with the same workload and model. The coursework's llama.cpp n-gram results are methodology, not performance predictions for L4/vLLM. The platform supplies capacity and telemetry; the app owns its model-server configurations and benchmark harness.

KFP driver/launcher and CPU validation pods should use the autoscaled `spot` group (`talos.dev/nodepool: spot`), with small explicit requests. Keep the serialized Spark dataset-build driver on the On-Demand `cpu` group (`talos.dev/nodepool: cpu`); avoid consuming its remaining reservation with orchestration pods. `ml` can query VictoriaMetrics at `http://vmsingle-vmks.observability.svc.cluster.local:8428/prometheus/api/v1/query`. KServe Serverless callers in `payment-gateway` should use `knative-local-gateway.istio-system.svc.cluster.local` with the InferenceService hostname in `Host`; enforce caller authorization at the gateway or a waypoint, because the predictor sees the gateway/activator identity after the proxy hop. A predictor-only principal rule cannot identify the original payment ServiceAccount.

## Ambient waypoints in `ml`

The `ml` namespace enforces `restricted` Pod Security, but istiod generates waypoint pods (`gatewayClassName: istio-waypoint`) without a seccomp profile. With `ambientWaypoint.enabled`, a `MutatingAdmissionPolicy` sets `seccompProfile: RuntimeDefault` on those pods only; every other `restricted` field is already set by the generated pod. It is on in dev and prod. The platform creates no waypoint, `HTTPRoute` or `istio.io/use-waypoint` label; consumers own those.

## Node-local LLM weights

KServe 0.21 local-model caching is enabled only in dev with `jobNamespace: kserve-localmodel`. The platform owns `LocalModelNodeGroup/llm-gpu` with a 40 GiB cache budget, static local PV templates at `/var/lib/kubelet/kserve-localmodel`, and a node agent on dev-server1. Production caching is disabled because no cloud GPU group is provisioned. Cache files are disposable on node replacement; `storageLimit` is cache accounting, not a filesystem quota. Keep disk headroom for images and other node data.

The app may own namespaced `LocalModelNamespaceCache` resources in `llm`, referencing `nodeGroups: [llm-gpu]`, with a pinned `sourceModelUri: hf://owner/model:commit`. Public Hugging Face repositories need no object-store credential. Downloads need Hugging Face and its CDN/Xet endpoints. Gated repositories need credentials in the download namespace; the cache's `serviceAccountName` selects credential lookup there, not the Job's Kubernetes ServiceAccount. A scoped native admission policy sets generated download Jobs to `kserve-localmodel-download` (no API token), non-root execution, bounded resources and the GPU-pool toleration. The node agent's hostPath setup is isolated in the privileged, unmeshed `kserve-localmodel` namespace; `llm` remains restricted and ambient. Cache consumers still need GPU DRA claims, placement and their GPU toleration. InstantTensor support and configuration belong to the app runtime image; local caching alone does not enable it.
