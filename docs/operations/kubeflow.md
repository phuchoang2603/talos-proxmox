# Kubeflow (prod)

The prod platform owns cert-manager, Istio ambient, the NVIDIA GPU operator, ESO/Doppler, local-path storage, and one shared Argo Workflows controller. The Kubeflow applications below are prod-only; no second copies of these shared controllers are installed. The charts are prepared in the working tree, **not deployed**; prod Doppler credentials were seeded on October 6, 2026, but the changes still need to be pushed and reconciled.

## Ownership and versions

- `apps/components/auth` supplies Dex 2.45.1 and OAuth2 Proxy 7.15.5. The chart uses external Secrets from the `doppler` ClusterSecretStore; no password, cookie secret or OIDC client secret is checked in. Both services run in `auth`.
- `apps/components/knative` supplies Serving and Eventing 1.23.0 with the cluster-local Istio gateway in `istio-system`. The ingress Gateway workload belongs to the shared `apps/components/istio` chart, enabled for prod only as an internal ClusterIP.
- `apps/components/kubeflow` enables the shared components from Community Distribution master revision `1e37b5db692624f65de04f30d5989e9651f20492` (2026-10-05): Trainer 2.3.0, Notebooks v1 1.11.0, Dashboard 2.0.0 with Profiles/KFAM, Katib 0.19.0, KServe and its UI 0.21.0/1.0.5, and Hub Catalog 0.3.17. The fraud repo owns its Profile and Hub Registry instance. Spark Operator 2.5.2 is the platform chart's only Helm dependency. The pinned upstream Kustomize outputs live in `files/`; the upstream sample passwords are removed. Kubernetes-native KFP is explicitly non-production upstream. Treat this prod-only deployment as experimental and do not use it with production data until end-to-end tests pass.
- Pipelines runs unreleased KFP master (3.0 development) from `kubeflow/pipelines` commit `ceb76061bf268f3ca10d6611b4daf8e8c78e64b7` (2026-10-06), with all images pinned to the immutable CI tag `run-37518086931-1`. Master removes ML Metadata, which is what limited KFP 2.x on PostgreSQL. It uses the single-user Kubernetes-native API on the CNPG `mlpipeline` database over TLS (`sslmode=verify-full` against the `kubeflow-pipelines-db-ca` CA). The API server runs `CREATE DATABASE` on every start, so the `kfp` role has CREATEDB. `files/pipeline/000.yaml` is rendered by `kubectl kustomize apps/components/kubeflow/vendor/pipeline`; re-render after changing that overlay or its pinned commit, and keep the image tags, `V2_DRIVER_IMAGE` and `V2_LAUNCHER_IMAGE` on the same build. The UI only reads artifacts from origins in `ALLOWED_ARTIFACT_ENDPOINTS`. Upgrading from 2.17.2 needs a one-time `kubectl patch` that replaced the UI Deployment strategy with `{type: Recreate}`: server-side apply cannot remove the defaulted `rollingUpdate` field. Since 2.18, pipeline uploads must name a namespace and viewing logs needs the `readLog` permission. Workspaces v2 is pre-GA and deliberately excluded.
- `apps/components/argo-workflows` remains the only Argo controller. It watches `kubeflow` and the consumer-owned `fraud-ml-prod` Profile namespace. The KFP overlay excludes the upstream Argo controller, its RBAC and configuration, and bundled MySQL and SeaweedFS; master has no v1 cache server. Local edits to the other vendored outputs: sidecar injection is disabled (ambient only), and upstream NetworkPolicies in `kubeflow` and `knative-serving` allow the ambient kubelet probe source `169.254.7.127/32` and HBONE port 15008. KFP retains its application controllers but uses two CNPG PostgreSQL clusters (KFP and Katib), an external RustFS bucket, and an artifact repository in `kubeflow`; the consumer owns its namespace-specific repository. It does not run bundled MySQL, PostgreSQL, SeaweedFS, or a second Argo controller.

The platform chart owns the Kubeflow Istio ingress configuration, not any user Profile. The Profile controller creates namespaces with the ambient mesh label. The prod-only `fraud-ml-prod` Profile, Hub Registry, registry database ExternalSecret, RustFS ExternalSecret, KFP launcher, and Argo artifact configuration are managed by `../realtime-credit-card-fraud-detection/infra/charts/kubeflow-workspace`. The consumer's Profile owner must match the Dex login identity configured in `apps/components/auth/values.yaml`. The consumer root must reconcile after the platform's CRDs and controllers; its child Application retries missing-CRD/namespace failures. Do not pre-create the Profile namespace with Argo CD `CreateNamespace`.

## Prerequisites before reconciliation

1. Authentication keys `AUTH_DEX_PASSWORD_BCRYPT`, `AUTH_OIDC_CLIENT_SECRET`, and `AUTH_OAUTH2_COOKIE_SECRET` are seeded in Doppler project `talos-proxmox`, config `prod`. A randomly generated login password is stored **only** in Doppler as `AUTH_DEX_PASSWORD`; retrieve it locally with `doppler secrets get AUTH_DEX_PASSWORD --plain --project talos-proxmox --config prod` (the command prints the secret). Do not commit or paste the password. ExternalSecrets must become Ready before testing login.
2. `KUBEFLOW_RUSTFS_ACCESS_KEY`, `KUBEFLOW_RUSTFS_SECRET_KEY`, `KUBEFLOW_KFP_POSTGRES_PASSWORD`, `KUBEFLOW_KATIB_POSTGRES_PASSWORD`, and `KUBEFLOW_CATALOG_POSTGRES_PASSWORD` remain in the platform Doppler project's `prod` config. The consumer owns its Hub Registry password, RustFS credential copies, and read-only ESO service token in the `realtime-credit-card-fraud-detection` Doppler project's `prd` config. The platform copy of `KUBEFLOW_REGISTRY_DB_PASSWORD` was removed after a verified transfer; neither repo stores secret values. The versioned RustFS bucket `kubeflow-prod-pipelines` and bucket-scoped service account were created and tested with an object round trip on October 6, 2026. The four obsolete KFP/Katib MySQL and SeaweedFS keys were removed from platform prod Doppler on October 6, 2026. Test a real KFP artifact upload after reconciliation. The upstream Hub Catalog still uses an ephemeral PostgreSQL volume and needs durable storage and backups before real data is stored.
3. The ingress service is **ClusterIP only**, not public. Defaults in the auth chart use an `http://localhost:8080` OIDC callback/login and insecure localhost cookie. For local evaluation, forward the ingress gateway Service on port 8080 and align Dex issuer, OAuth2 callback/login, and allowed client redirect if changing the URL. For public access, configure a real HTTPS hostname, TLS, HTTPS-only cookies and authenticated Gateway policy first; never expose this HTTP/local configuration.
4. Reconcile the platform before the consumer root. The Profile controller creates `fraud-ml-prod` with `istio.io/dataplane-mode: ambient`; the consumer's workspace and separate generic secret-store Applications retry until that namespace and the platform CRDs exist. Once the namespace exists, provision `fraud-doppler-token` in it with key `dopplerToken` from the fraud Doppler project's `prd` config; platform ESO cannot read the fraud project. The same generic store runs on dev in `payment-gateway` with its own Doppler `dev` token, without Kubeflow. Both `kubeflow` and `fraud-ml-prod` need their RustFS ExternalSecret, `artifact-repositories` and `kfp-launcher` ConfigMaps ready before starting workflows. A healthy Application alone is not proof of working workloads.

## Validation

Use `devenv shell` for `helm lint` and `helm template` in both repos; supply `--api-versions cert-manager.io/v1/Issuer --api-versions cert-manager.io/v1/Certificate` to template Spark Operator. Check the prod platform and consumer Applications and absence of auth/Knative/Kubeflow on dev. Then verify the ExternalSecrets in both namespaces, both CNPG Clusters, Dex and proxy readiness, Knative Serving and Eventing, KServe webhooks, and the Dashboard via the internal gateway. Prove one persistent GPU notebook in the consumer Profile, one Kubernetes-native KFP Pipeline/PipelineVersion and a KFP run on the shared Argo controller with a stored RustFS artifact (including upload and download via the UI), one Katib experiment, and authenticated `/pipeline/`, `/jupyter/`, and `/katib/` before declaring the rollout complete. Measure scheduling against ClickStack, Kafka and other production services; local-path PVCs are node-bound; both CNPG Clusters have one instance and are not HA. Test restore before storing valuable data.

A bounded CUDA smoke Job already passed on prod-server1 on October 6, 2026 (Job `default/kubeflow-gpu-smoke-20261006`, CUDA result 42). This verifies GPU scheduling and execution only; it does not prove Kubeflow workload integration.
