# Kubeflow

Both environments own cert-manager, Istio, ESO/Doppler and one shared Argo Workflows controller. Dev uses local-path and its local GPU; prod uses gp3 EBS and optional cloud GPU capacity. Kubeflow uses those shared controllers in each environment.

## Ownership and versions

- `apps/components/auth` supplies Dex 2.45.1 and OAuth2 Proxy 7.15.5. The chart uses external Secrets from the `doppler` ClusterSecretStore; no password, cookie secret or OIDC client secret is checked in. Both services run in `auth`.
- `apps/components/knative` enables pinned Serving and Eventing 1.23.0 and net-istio in both environments. KServe uses `Serverless` mode, including Knative request-based scale-to-zero. The external ingress and cluster-local gateways use the shared Istio deployment and internal ClusterIP Services.
- `apps/components/kubeflow` enables the shared components from Community Distribution master revision `1e37b5db692624f65de04f30d5989e9651f20492` (2026-10-05): Trainer 2.3.0, Notebooks v1 1.11.0, Dashboard 2.0.0 with Profiles/KFAM, Katib 0.19.0, KServe and its UI 0.21.0/1.0.5, and Hub Catalog 0.3.17. The fraud repo owns its Profile and Hub Registry instance. The pinned upstream Kustomize outputs live in `files/`; the upstream sample passwords are removed. Kubernetes-native KFP is explicitly non-production upstream. Treat this deployment as experimental and do not use it with production data until end-to-end tests pass.
- Pipelines runs unreleased KFP master (3.0 development) from `kubeflow/pipelines` commit `ceb76061bf268f3ca10d6611b4daf8e8c78e64b7` (2026-10-06), with all images pinned to the immutable CI tag `run-37518086931-1`. Master removes ML Metadata, which is what limited KFP 2.x on PostgreSQL. It uses the single-user Kubernetes-native API on the CNPG `mlpipeline` database over TLS (`sslmode=verify-full` against the `kubeflow-pipelines-db-ca` CA). The API server runs `CREATE DATABASE` on every start, so the `kfp` role has CREATEDB. `files/pipeline/000.yaml` is rendered by `kubectl kustomize apps/components/kubeflow/vendor/pipeline`; re-render after changing that overlay or its pinned commit, and keep the image tags, `V2_DRIVER_IMAGE` and `V2_LAUNCHER_IMAGE` on the same build. The UI only reads artifacts from origins in `ALLOWED_ARTIFACT_ENDPOINTS`. Upgrading from 2.17.2 needs a one-time `kubectl patch` that replaced the UI Deployment strategy with `{type: Recreate}`: server-side apply cannot remove the defaulted `rollingUpdate` field. Since 2.18, pipeline uploads must name a namespace and viewing logs needs the `readLog` permission. Workspaces v2 is pre-GA and deliberately excluded.
- `apps/components/argo-workflows` remains the only Argo controller, deployed in `operators` and watching `data` and `ml`. Kubeflow, KServe, JobSet and Trainer resources share `ml`; Kubeflow owns its Namespace and ambient/Pod Security labels. The KFP overlay excludes the upstream Argo controller, bundled databases and SeaweedFS. KFP and Katib each use single-instance CNPG PostgreSQL, external object storage and the artifact repository in `ml`.

The platform chart owns the Kubeflow Istio ingress configuration and the `ml` Namespace. External application charts must target `ml` for ML workloads and `data` for data jobs, update their service references, and avoid owning or deleting the platform Namespace through an application Profile. Their identity must match Dex configuration in `apps/components/auth/values.yaml`.

## Validation

Use `devenv shell` for `helm lint` and `helm template` in both repos. Check platform and consumer Applications in the matching environment, including auth, Knative and Kubeflow in both. Then verify the ExternalSecrets in both namespaces, both CNPG Clusters, Dex and proxy readiness, KServe webhooks, and the Dashboard at <https://kubeflow.phuchoang.sbs>. Prove one persistent GPU notebook in the consumer Profile, one Kubernetes-native KFP Pipeline/PipelineVersion and a KFP run on the shared Argo controller with a stored RustFS artifact (including upload and download via the UI), one Katib experiment, and authenticated `/pipeline/`, `/jupyter/`, and `/katib/` before declaring the rollout complete. Measure scheduling against the Victoria telemetry stores, Kafka and other services; local-path PVCs are node-bound; both CNPG Clusters have one instance and are not HA. Test restore before storing valuable data.

A bounded CUDA smoke Job already passed on prod-server1 on October 6, 2026 (Job `default/kubeflow-gpu-smoke-20261006`, CUDA result 42). This verifies GPU scheduling and execution only; it does not prove Kubeflow workload integration.

GPU allocation uses the NVIDIA DRA driver on both local and AWS nodes; the traditional NVIDIA device plugin is disabled. Karpenter 1.15.1 enables the alpha `settings.awsFeatureGates.draNVIDIAGPU` gate to model NVIDIA devices before launching nodes, including `g6.xlarge` from zero. It waits for the DRA driver's ResourceSlices rather than requiring device-plugin GPU capacity for DRA claims. The AWS GPU NodePool advertises `nvidia.com/gpu.present=true` so the driver can start on the custom Talos AMI. Prod GPU pool limits permit one GPU worker. Runtime `aws-gpu-training` uses the namespaced `ResourceClaimTemplate/aws-gpu-training`, provisioned in `ml`, for explicit DRA allocation from zero capacity.

GPU workloads must use explicit namespaced `ResourceClaim` or `ResourceClaimTemplate` references, with `deviceClassName: gpu.nvidia.com`, `spec.resourceClaims` on the pod and `resources.claims` on each GPU container. For Notebooks these fields belong under `spec.template.spec`; Jobs, training workloads and KServe Standard predictors must carry the equivalent pod/container fields. The Jupyter GPU-count dropdown and `limits: nvidia.com/gpu` use extended-resource requests, which Karpenter does not recognize as DRA requests for provisioning. The DeviceClass retains its Kubernetes compatibility mapping, but use explicit claims for workloads so AWS can provision from zero. Do not patch Node GPU capacity.

The NVIDIA DCGM exporter collects GPU metrics every 60 seconds with DRA pod attribution enabled. The observability chart installs the Prometheus-compatible ServiceMonitor, PodMonitor, Probe, PrometheusRule and ScrapeConfig CRDs; the VictoriaMetrics operator converts these resources into native scrape and rule resources. NVIDIA's ServiceMonitor is converted into a VMServiceScrape for vmagent; the exporter has read-only ResourceSlice RBAC for DRA device mapping. Grafana provisions the NVIDIA DCGM Exporter dashboard from NVIDIA's `dcgm-exporter` tag `4.8.4`, using the `VictoriaMetrics` datasource.
